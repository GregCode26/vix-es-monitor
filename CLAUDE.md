# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal market dashboard ("Greg Dashboard") with three areas:
- **Market Monitor** (`/market`): live VIX + ES=F (S&P futures) intraday chart
- **SPX Volumes / GEX** (`/spx-volumes`, `/gex`, `/spx-gamma`): 3D and gamma-exposure visualizations of SPX option data
- **Finance Input** (`/input`): manual personal transaction log written to a local CSV

Frontend is Next.js (App Router), deployed to Vercel. Data collection is done by local Python scripts talking to Interactive Brokers TWS, which is only reachable when running on the developer's own machine — this is fundamentally a local-first tool with a cloud-deployed viewer.

Auth is a hardcoded client-side check (`Gregorio` / `Pinzolo26` in `frontend/src/app/login/page.tsx`) storing `market_auth` in `localStorage`. This is intentional for a single-user private tool — do not "fix" it into a real auth system unless asked.

## Commands

Frontend (run from `frontend/`):
```bash
npm run dev      # http://localhost:3000
npm run build
npm run lint
```

Python (run from repo root):
```bash
pip install -r requirements.txt
pip install ib_insync          # not in requirements.txt but required by pollers

python execution/tws_poller.py          # VIX + ES=F + SPX poller (needs IBKR TWS running locally, port 7496)
python execution/tws_volumes_poller.py  # SPX option volume-by-strike poller
python execution/tws_iv_poller.py       # SPX 0DTE ATM implied volatility monitor (bid/ask/IV per option)
python execution/backfill_ibkr.py       # 1-min historical backfill for VIX/ES
python execution/init_db.py             # verify Supabase connectivity / print bootstrap SQL
python execution/check_sync.py          # read latest Supabase rows for today
```

`start_dashboard.bat` (Windows) opens the browser and hands off to `scripts/keep_dashboard_alive.ps1`, a supervisor that keeps `npm run dev` up (restarting it 15s after any exit) and POSTs `/api/poller` every minute so a poller that dies with TWS comes back. It does not launch the pollers itself: they start with the server via `frontend/src/instrumentation.ts` (skipped on Vercel, or with `AUTO_START_POLLERS=false`).

**The supervisor is registered as a logon task, so nothing has to be launched by hand.** Scheduled task `GregDashboard` (AtLogon, 30s delay, no execution time limit, no elevation) runs the same script hidden. This exists because the retry wrapper inside each poller survives TWS disconnecting and the day rolling over, but not the machine being switched off: on 21/08/2026 the logs stopped at 22:05 the previous night mid-retry and nothing ran until 16:05, losing two and a half hours of the session. Starting a second supervisor is harmless — it checks whether port 3000 already answers before starting a server, so it will not put Next on 3001. Inspect it with `Get-ScheduledTask GregDashboard`, disable it with `Disable-ScheduledTask GregDashboard`.

There is no automated test suite in this repo.

## Architecture

### Data flow: pollers → files/Supabase → API routes → chart

**Every poller runs sessions, not one endless loop** (`execution/poller_session.py`). A session = connect, pick today's 0DTE chain, subscribe, poll; it *ends* when the day changes, and `esegui_a_oltranza()` starts a fresh one 30s later. This is not decoration: the date key for the output file was recomputed every iteration but the 0DTE expiry was chosen once at startup, so past midnight a poller looked healthy and wrote to the right file while subscribed to expired contracts. The same wrapper turns two other fatal cases into retries — TWS restarting overnight (`ConnectionError: Socket disconnect` used to kill the process) and data not being ready yet (every `CRITICAL: ...` was a `return`, i.e. permanent death; the IV poller restarted at 08:27 CET died because SPX cash does not print before 15:30). Do not "simplify" a poller back into a single `main()` loop, and keep the `spx_ticker.close` fallbacks — they are what let a poller come up before the cash open.

**Cash-session times are New York times, converted every time** — `minuti_locali_da_ny()` in `poller_session.py` for the pollers, `frontend/src/lib/orarioNy.ts` (`oraRomaDaNy`/`minutiRomaDaNy`, explicit `Europe/Rome`, so also correct on Vercel's UTC) for the frontend. Italy and the US change clocks on different Sundays: from the last Sunday of October to the first of November (and 2-3 weeks in March) the cash opens at 14:30 Italian time, the OB range/straddle cone are at 14:35 and the close is 21:00. Hardcoded `15:30`/`15:35`/`22:00` were an hour late those weeks (noticed 26/10/2026). The volumes and IV poller windows are 7:30-16:00 NY (13:30-22:00 most of the year). The morning range at 10:35 is an Italian time and stays fixed. Do not write new cash-session times as Italian constants.

Python pollers (`execution/tws_poller.py`, `execution/tws_volumes_poller.py`) connect to a locally running IBKR TWS instance, pull market/option data, and write JSON snapshot files. `tws_poller.py` also optionally pushes rows to Supabase (`push_to_supabase()` currently only sends `vix`, `esf`, `time`, `date` — NOT the derived `volTide`/`coneUp`/`coneDown` fields, so anything relying on those cloud-side will not find them).

Next.js API routes (`frontend/src/app/api/*/route.ts`) read this data back out:
- `GET /api/market` — Supabase first if configured, else local JSON fallback. No params = latest point; `?history=true` = today's intraday series. **Today only** — there is no `?date=` and no archived-session branch. **The local file `frontend/data/market/YYYY-MM-DD.json` keeps the whole day** (`tws_poller.py`): it used to be trimmed to the last 100 points (~25 min) as a mere fallback, and on 13/10/2026, with Supabase switched off, that dropped the 15:35 straddle point the OB ranges are computed from — the ranges vanished from `/market`, `/bookmap` and Quantower. Do not trim it again while it can be the only history.
- `GET /api/volumes` — Supabase table `volumes_snapshots` (una riga per snapshot) first, local JSON fallback. **Today only**, no `?date=`; `?since=HH:MM:SS` returns only the snapshots after that time, which is how the page stays cheap — it fetches ~2 KB every 30s instead of re-downloading the session.
- `GET /api/gex` — **real** gamma exposure, computed in TypeScript from the same `volumes_snapshots` rows `/api/volumes` reads: gamma comes from the IBKR `modelGreeks` the volumes poller already subscribes to. This replaced the old synthetic generator (the port of `execution/gexbot.py`, still on disk but no longer invoked by anything). Every point carries two measures and the page switches between them without refetching: `gex` weighted by volume traded (a **flow** measure) and `gexOi` weighted by open interest (**positioning**, the canonical GEX — flat intraday, since OI is frozen at the previous close). The call-positive/put-negative sign is still the standard "dealers long calls, short puts" heuristic, not observed data. A third measure, `gexLr`, does use observed sides: the volumes poller classifies every volume increment with Lee-Ready (quote rule against the bid/ask in force *before* the trade, tick test at the mid; class `LeeReady`) and writes per-strike `cb/cs/pb/ps` (calls/puts bought/sold by customers today) into each snapshot row; dealers hold the opposite, `-(cb-cs)-(pb-ps)`. It only covers contracts classified since the poller started counting (`inizioLr` in the response), not positions opened earlier. The response carries `points` (flow bubbles), `profile` (day total per strike), `spot` (the underlying as IBKR valued the gamma, one point per ~30s — the right series for a gamma page, unlike `/api/market` with its hand-rolled timezone shift), and `profileHistory` (the profile as it was 1/5/10 minutes ago, computed only on the full load — an incremental window is a few seconds wide and could not contain it). **Today only**, no `?date=`; supports `?since=` like `/api/volumes`, plus `?flow=0` to drop the bubbles (474 KB → 27 KB for a full session); the first load is truncated to the last ~8000 flow points (the cumulative `profile` is unaffected). Returns **503 when there is no gamma yet** — the volumes poller only collects between 13:30 and 22:00, so this is the normal answer in the morning, not a failure.
- `GET /api/iv-monitor` — **implied volatility changes** for SPX 0DTE options near ATM. Collects bid/ask/IV from IBKR via `tws_iv_poller.py` (separate from the volumes poller). Response includes weighted PUT IV and weighted CALL IV (weighted by distance from ATM), calculated IV change % (default 1-min lookback), and a differential (PUT change − CALL change) measuring volatility skew. No params = today's full session; `?since=HH:MM:SS` returns only snapshots after that time; `?limit=N` caps results. Reads from Supabase `iv_snapshots` table if configured, else local JSON fallback (`frontend/data/iv-monitor/YYYY-MM-DD.json`). **Today only**, no `?date=` — same rule as the other routes. **Read incrementally via `?since=`**: a snapshot is ~1.3 KB and one arrives every 5 seconds, so a full session is ~8 MB and the page polls every 5s; fetching the whole day each time was ~700 full-session downloads per hour against the Supabase egress budget. The table is `sql/002_iv_snapshots.sql` (it did not exist until 21/08/2026, so every push failed with PGRST205 while the local JSON fallback quietly hid it). **The poller must never write NaN**: `json.dump` emits bare `NaN`, which is not JSON, and `JSON.parse` then rejects the *entire file* — one missing IBKR price cost the whole 7.3 MB session of 20/08/2026. `_senza_nan()` maps it to `null` before both the file write and the Supabase push.
- `GET /api/verticali` — execution cost of every 5-point SPX 0DTE vertical, call and put, from `frontend/data/catena/quote.json`: the last bid/ask of the volumes poller's 37 strikes, **overwritten** every 10s by `scrivi_quote()` (no history, no Supabase, no extra market data lines — same tickers). Each side shows the mid plus `vol` (contracts of that vertical executed today, comprati/venduti/incerti) and the response carries `blocchi` (executed verticals ≥100 contracts). These come from `execution/verticali_blocchi.py` (`RilevaVerticali`, hooked into the volumes poller's `pendingTickersEvent`), which reads every trade via **RTVolume** (generic tick 233) and appends to `frontend/data/verticali/YYYY-MM-DD.ndjson`: two trades on the same side, K/K+L (L a multiple of 5 up to 50 since 29/10/2026 — only 5 before, which missed a 3,000-lot 7670/7680 on 28/10; only 5-point blocks feed the table rows, wider ones only the list), same size (≥5), within 0.5 s, with the combo price between credit and debit of the quotes in force before; direction from price vs the vertical's mid; pieces on the same vertical within 1 s merged. Why RTVolume (tested 27/10/2026): IBKR historical ticks for SPXW carry no OPRA condition codes (0 of 5,639 trades), tick-by-tick AllLast is refused on SPXW (error 10189), while RTVolume summed sizes matched the `volume` increase within 0-4% on 6 ATM contracts over 120 s. Counting starts when the poller starts — trades before a restart are not recovered. Local and today only; 503 until the poller has written today. `?sim=1` returns a fake Black-Scholes chain (`sim: true`) so the page can be seen with the market closed — the page's SIMULAZIONE button, with an amber banner.
- `GET /api/smile` — SPX 0DTE IV smile with the convexity ladder, for the curve on the right of `/market` (the "Optix Smile" formulas). `quote.json` also carries per-strike call/put IV and delta (IBKR `modelGreeks`), gamma and Lee-Ready `cb/cs/pb/ps`; `execution/smile.py` turns it into one reading per poll (sections 1-6: smoothed ATM IV, expected move to 16:00 ET, 25-delta IVs, Tilt = Put25−Call25, Curv = mean(25Δ)−ATM, IV MIN vertex), stored in `quote.json` and appended to `frontend/data/smile/YYYY-MM-DD.ndjson`. The route does sections 7-8: z-scores against past days at the same ET time ±15 min (≥3 days, ≥15 readings), else a provisional base of today's last 60 min (≥10), else "in raccolta"; then the regime, which only changes after 2 consecutive new readings agree. Arrows are the **convexity ladder**: taker net gamma per strike, i.e. `gexLr` of `/api/gex` with the opposite sign. Unlike the original there is no 15-minute delay (it existed only because the Cboe data was delayed). **Do not leave test readings in today's ndjson**: they become part of the z-score base. Local and today only. **Version 2 since 27/10/2026** (field `v` of each reading): IV and delta are computed in `smile.py` from the bid/ask mid (Black-76 on the put-call-parity forward), `modelGreeks` only as fallback on a side without a usable mid (on 26/10 the model IV ATM repeated itself in 1,720 of 2,227 readings); IV ATM interpolated at spot; the regime runs on `tiltN`/`curvN` (Tilt/Curv as % of IV ATM), with hysteresis (enter |z| ≥ 1, leave < 0.5), majority confirmation (≥70% of the last 90 s, not "90 s in a row", which never confirmed anything on noisy data), the reading excluded from its own provisional base, and suspended from 15:15 ET; the vertex changes strike only if 0.1 vol lower. v1 readings stay in the files but are excluded from the z-scores, so the historical base restarts from 27/10. After the close (`quote.json` without a smile) the route still answers 200 with `chiuso: true`, empty `punti` and the day's `storiaVertice`, so the violet IV MIN trace stays on `/market` (28/10/2026: at 21:00 it vanished with the 503). `?giorni=N` (max 10) returns only the IV MIN traces of the N previous days, each with that day's ES−SPX basis (median over the hours of its readings, from `market/YYYY-MM-DD.json`) and its last reading time — for Quantower, whose chart shows past days too; it answers even before the open, when the plain call is 503.
- `GET /api/market-tide` — the "Market Tide" (net call/put premium and net volume, ask side minus bid side, cumulative over the day) of the SPX 0DTE chain, from the `tide` field of each volumes snapshot (Supabase column `tide`, sql/006, else the local file); `?since=` like `/api/volumes`. **Version 2 since 29/10/2026** (`tide.v`), computed trade by trade in `MarketTide` from the RTVolume trades `RilevaVerticali` already reads: each trade against the bid/ask in force *before* it (above the mid bought, below sold, at the mid ignored), and the two legs of a detected vertical counted **once**, at the spread's price and in its direction. Why (`execution/studio_tide.py`, 14 sessions): v1 compared the last price of each 10 s volume increment with the *current* bid/ask, already moved by the market, so when SPX rose puts looked bought and calls sold — the net Tide correlated −0.28 with SPX in the same 5 minutes, i.e. it read the move backwards (Lee-Ready, with the quote before the trade: ±0.04); and vertical legs counted twice at full premium — a deep ITM 7670/7680 call vertical of 3,000 lots on 28/10 made +40M of NCP for a spread worth at most 3M. No flow measure tested forecast SPX over the next 15 minutes (all −0.04…−0.08): read it as who is buying what, not as a signal. The route keeps only the day's latest version, since v2 restarts from zero. v1 totals are never resumed.
- `POST /api/bookmap` / `GET /api/bookmap` — ES CVD and book liquidity from **Bookmap**, local only (no Supabase: ~80.000 samples/day would not be worth the egress). `execution/bookmap_addon.py` is not launched by us: it is a Bookmap Python add-on (built from Bookmap's *API plugins configuration*) that POSTs one sample per second (~1 KB, including the limit-order levels — ≥20 contracts within 30 ticks of the best, ≥50 from there out to 120 ticks (27/10/2026: with 30 ticks only, a 7750 wall visible in Bookmap with ES at 7731 never reached the page or Quantower) — that the page draws as Bookmap-style horizontal lines, and the limit contracts added/removed within 5 levels of the best on each side, counted on every depth update, plus the per-level Order Flow Imbalance of the first 15 levels — Cont/Kukanov/Stoikov OFI and its multi-level MLOFI, computed between 100 ms book snapshots — and each side's liquidity centroid in ticks from mid, best-level queue, mean queue per level and 1-tick-spread share, plus detected **absorptions** — aggressive volume at one price ≥ 2× the queue there, with the level still holding afterwards; the page filters them by size and draws them as balls). **There is no stop detection, on purpose** (removed 05/10/2026): it looked for several aggressors inside one matching event, but on Rithmic every event has exactly one (0 of 126k), and the fallback — bursts of same-side events a few ms apart — matched Bookmap's own Stops & Icebergs poorly, mixing stops with iceberg refills and split orders. That add-on reads the book order by order (MBO); from trades alone stops cannot be separated, so do not bring it back without MBO data, sending from a background thread so Bookmap's callbacks never wait on the network. The route appends to `frontend/data/bookmap/YYYY-MM-DD.ndjson` and computes the CVD itself as the day's running sum of `buy - sell`, so restarting Bookmap does not reset it. Today only, `?since=HH:MM:SS`. On Vercel GET answers `local: false` and the page says so. After editing the add-on, copy it to `C:\Bookmap\Python\` and rebuild it from Bookmap's code editor (runtime set to the system `python.exe`, since Bookmap looks for a `python3` that Windows does not have). **Keep every block header (`for`/`if`/`def`...) on one line in the add-on**: Bookmap's code editor crashes with a `NullPointerException` in `PythonFoldParser` on a header split across lines, and then the file cannot be opened or rebuilt (05/10/2026).
- `POST /api/poller` — spawns the pollers as detached background processes via `child_process.spawn('python', ...)`, one log each under `.tmp/poller-logs/`. Only works when the API itself is running locally (there's a "start pollers" button in the UI backed by this route, `PollerButton.tsx`; `instrumentation.ts` also calls it at server boot, and `scripts/keep_dashboard_alive.ps1` POSTs to it every minute). **A live PID is not proof a poller is running:** `frontend/src/lib/pollers.ts` verifies the process's actual command line (`Get-CimInstance Win32_Process` on Windows, `ps -o pid=,args=` elsewhere) before trusting `.tmp/pollers.lock`, because Windows recycles PIDs fast — a stale lock pointing at a recycled PID once made the pollers look alive for a whole day while nothing was collected. Restart is per-script, so one dead poller comes back without waiting for the other to die too. Do not "simplify" this back to `process.kill(pid, 0)`.
- `POST /api/finance` / `GET /api/finance` — writes to / reads from the Supabase `transactions` table, falling back to appending `.tmp/transactions.csv` when Supabase is not configured. The old `spawn('python3', ...)` is gone (it never worked on Windows and never worked on Vercel).

**Supabase egress is the binding constraint, not database size.** The free tier allows ~5 GB/month of egress, and the volumes path is what spends it: every extra KB moves ~3.000 times a day. Two rules keep it in budget — writes from the pollers must pass `returning="minimal"` (PostgREST otherwise echoes the whole inserted row back), and the volumes page must fetch incrementally via `?since=`. Reverting either one costs hundreds of MB per trading day. See `sql/001_volumes_snapshots.sql`. The same holds for **every caller of `/api/gex` and `/api/volumes`, local ones included**: with Supabase configured the local server reads from it too, so a call without `since` pulls the whole session (12-17 MB by the close). In October 2026 the Quantower indicator (every 15s) and `/ook` (every 5s) did exactly that and the project was suspended for `exceed_egress_quota` (HTTP 402); both now send `since`, starting from the last 5 minutes, since `profile` is already the day total.

**Known path inconsistency (real, not hypothetical):** pollers write market/volume JSON to `frontend/data/market` and `frontend/data/volumes`, while a root-level `data/market/` and `data/gex/` also exist and some routes resolve paths via `process.cwd()` in ways that assume Next was started from a specific directory. If a change touches file read/write paths, check the actual `path.join`/`path.resolve` calls in the specific route rather than assuming a single canonical data directory — the routes are not all consistent with each other yet.

### Frontend chart pages

- `frontend/src/app/market/page.tsx` — main Chart.js dashboard. Trading window is `00:05`–`23:00` CET; a 30s watcher detects session start/end and resets `localStorage` (`marketData_YYYY-MM-DD`) at `00:05`. Polls `/api/market` every 5s during the window. Custom auto-scroll logic: chart tracks live data at the right edge unless the user has manually panned back, in which case tracking locks until "RESTORE LIVE VIEW" is clicked. Also hosts the "Range Calc" panel (implied-volatility range model off ATM straddle prices entered manually at 10:35/15:35) which computes R1/R2/R3 reference lines and can push them onto the chart. **Keys and displayed names differ for R1/R2** (since 21/10/2026, names now follow distance from spot): key `r2*` (straddle/√3, the closest) is shown as **R1**, key `r1*` (straddle) as **R2**, `r3*` stays R3. Only the labels were swapped — keys, values, colours and localStorage/Supabase fields are unchanged — so when adding a label anywhere (pages, Quantower) map the key to the name, do not print the key number.
- `frontend/src/app/spx-volumes/page.tsx` — `echarts` + `echarts-gl` 3D view of call/put volume by strike over time, polling `/api/volumes` every 10s.
- `frontend/src/app/gex/page.tsx` — Chart.js view of the GEX **flow** over time (the `points` bubbles), reading `/api/gex` incrementally via `?since=` plus `/api/market?history=true` for the spot line.
- `frontend/src/app/spx-gamma/page.tsx` — `echarts` view of the GEX **profile by strike**: bars per strike, the spot scrolling alongside on a second (time) x-axis, and white dots showing the same profile 1/5/10 minutes ago. Fetches `/api/gex?flow=0` (it draws the profile, not the bubbles — the flow is ~95% of the payload) every 15s. Major Pos/Neg Gamma are derived from the profile. **There is no Zero Gamma anywhere, on purpose** (removed 05/10/2026, along with `lib/zeroGamma.ts`): the volumes poller only follows 0DTE and 37 strikes around ATM, and with the chain that incomplete the level cannot be computed reliably — the old cumulative-sum version put it at 7752 with SPX at 7734, a full-revaluation attempt still landed 5-15 points off an external reference. Do not add it back from this data. Both bases are on one axis via a selector: on 0DTE the volume-weighted numbers run ~20× the OI-weighted ones, so showing them together by default would flatten the OI bars onto zero. **Values are in $M in the API and rendered as $Bn in this page** — check `inMiliardi()` before comparing numbers across the two pages.
- `frontend/src/app/operativita/page.tsx` — the 5-point verticals from `/api/verticali` (every 10s): a "Blocchi di vertical" list (the latest executed verticals above a 100/250/500/1000 threshold, named bull/bear call/put) and the per-strike table centred on the ATM vertical (spot between the strikes, yellow line) with Mid | Comprati | Venduti per side and a ×N badge for blocks above the threshold. The "execution cost" cards were removed 27/10/2026 at the user's request. VWAP and the R1/R2/R3 OB ranges are tagged on the vertical that contains them, **in SPX prices**: ES VWAP minus the live ES−SPX basis from `/api/market`, and `range.ob` (ES prices) minus its own 15:35 `basis`, with the `/market` panel's manual edits and visibility applied as in `/bookmap`. Estimating customers' verticals from the Lee-Ready increments (10s cumulative volume) was tried and parked (25/10/2026): with ≥10 contracts per leg most pairs are coincidences — hence the per-trade RTVolume detector.
- **Smile curve on `/market`** (`frontend/src/lib/smileChart.ts`, "Smile" button) — drawn in an empty axis `y-smile` (weight 0, so it sits between the plot and `y-right`, which got weight 1), 180 px wide or 0 when off. Y = SPX strikes moved onto the ES scale with `chart.$basisSpx`, so nothing is drawn before the 15:30 cash open. X = IV, scaled on the strikes currently visible. Grey line on the OTM IV, green dot = call IV, red = put IV (the non-OTM one stays detached), hollow beyond ±2σ; orange arrow from the left = takers short convexity, cyan from the right = takers long. Header text: regime, ATM IV, 1σ, IV MIN, z-scores. Horizontal lines across the whole chart (added 26/10/2026, after the user first asked for none): Spot ±1σ (long dash), ±2σ (dotted) and the IV MIN vertex (violet), labelled in SPX prices inside the column. The violet line is not horizontal: it steps through the vertex strike over time (`storiaVertice` in `/api/smile`, only the strike changes, ~60 a session), all moved onto ES with the current basis. In a fresh headless Chrome profile `/market` stays empty on first load (the chart ref points at a destroyed instance until a reload uses the localStorage cache) — a pre-existing quirk, unrelated to the smile.
- `frontend/src/app/iv-monitor/page.tsx` — Chart.js dashboard monitoring real-time **implied volatility changes** for SPX 0DTE options. **The page computes the % changes itself** from the IV levels, with the lookback picked in the selector (the `*ChangePct` fields the poller wrote were always 0 until 13/10/2026: the history is filled with `appendleft`, and the lookup read it newest-first, comparing each value with itself). It also draws ES in yellow on its own right-hand scale (history loaded once, then only the latest `/api/market` point), with a crosshair instead of the tooltip and zoom per scale. Tracks weighted IV for PUT and CALL near ATM, displays IV change % over user-selected lookback period (5s/30s/1m/5m), and a differential chart showing PUT−CALL IV skew. Polls `/api/iv-monitor` every 5s during active hours. Controlled by `execution/tws_iv_poller.py` which connects to IBKR and collects IV bid/ask data every 5 seconds. Its ATM ± 2 strikes are re-centred in place (`centra()`, no session restart) when spot moves ¾ of a strike away: until 25/10/2026 they were picked once at startup, often off yesterday's close, and on 23/10 all five ended up above spot. See `context/IV_MONITOR_SETUP.md` for full setup and interpretation guide.
- Chart updates should stay imperative (`chart.data... ; chart.update('none')`) to avoid resetting user zoom/pan state — this is the existing convention in `market/page.tsx`, follow it in other Chart.js views.

### Quantower indicator

`quantower/GregDashboard/` is a C# Quantower indicator (.NET 8, references `TradingPlatform.BusinessLayer.dll` from the Quantower install) that draws the dashboard onto an ES chart: range R1/R2/R3 OB (and morning, off by default) from `/api/market?history=true`, the GEX profile by strike on the right edge with SPX strikes shifted into ES by the ES−SPX basis (5-minute median of `/api/market` readings, same as `/bookmap`, `/market` and `/operativita` — **cash-session readings only, 9:30-16:00 NY**: after the close IBKR leaves SPX frozen at its last value while ES keeps trading, and on 28/10/2026 the "basis" drifted from 35 to 16.8 by 22:00, shifting the SPX column, smile and GEX by 18 points; after the close the last cash value holds; settable by hand, since there is no basis before the 15:30 SPX cash open), and Bookmap liquidity lines rebuilt with the same segment algorithm as `/bookmap` from `/api/bookmap?since=`, plus the absorptions — drawn as arrows, not the page's balls (since 29/10/2026, at the user's request): blue pointing up when limit buyers absorb market sells, red pointing down when limit sellers absorb market buys, tip on the absorption price; same size rule and minimum-size filter as the page, and a hold setting of 1-10 s: beyond the add-on's own 1 s the indicator checks the per-second bid/ask itself and shows an arrow only once its level has stayed at the best that long; `execution/studio_assorbimenti.py` found no hold length that beats a random level held as long), and the `/market` smile column (`DisegnaSmile`, a C# copy of `lib/smileChart.ts`: curve, call/put dots, convexity arrows, header, Spot ±1σ/±2σ and the stepped IV MIN line, plus the stepped lines of the last 5 days from `/api/smile?giorni=5`, re-read every 30 minutes and at midnight) left of the GEX profile, from `/api/smile` every 10s and moved onto ES with the same basis as the GEX — keep the two in sync when the page's smile changes. The same DLL holds a second indicator, `GregMlofi` ("Greg MLOFI", separate panel): the `/bookmap` MLOFI (`mlofiMobile()`: OFI of the first N levels summed over a rolling window, divided by N × the window's mean queue) ported to C# and painted like the page (per-second line, green above zero / red below, area filled to zero) via `OnPaintChart` on `CurrentChart.Windows[args.WindowIndex]`; its two line series are transparent and exist only to give Quantower a symmetric autoscale (+/- the max |MLOFI| of each candle). It only reads the existing APIs, so the dashboard must be running. Bookmap times are this PC's local time and are converted to UTC for `GetChartX`. `dotnet build -c Release` from that folder builds it and copies the DLL into `%USERPROFILE%\Documents\AMP Quantower\Settings\Scripts\Indicators\`, next to the other custom indicators. **The Quantower in use is the AMP one in Documents, not `C:\Program Files\Quantower`** (a different install that is not the one launched); the indicator is applied on MES, which trades at the same price as ES. `QuantowerBin` in the csproj points at the versioned install folder (`v1.141.4`) and must be updated after a Quantower upgrade.

### Persistence layers in play simultaneously

- Browser `localStorage`: daily market cache, reference lines + visibility, auth token.
- Local filesystem: JSON snapshot files (see path caveat above); `.tmp/transactions.csv` for finance entries.
- Supabase (Postgres): optional — used by the market/volumes/gex/iv-monitor/finance routes, each with a local file fallback. Env vars for it live in `frontend/.env.local` and `execution/.env` (see those files for the current key names — do not print their values).

On Vercel, only `/tmp` is writable and is wiped on cold start, so file-backed history does not persist there — Supabase (where wired up) is the only durable cloud store today.
